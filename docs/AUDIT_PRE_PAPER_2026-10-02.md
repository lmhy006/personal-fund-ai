## 3. 首次确认前应修复的代码问题

### P0-1：真实 CSV 重载后，首次确认会直接失败

位置：[live_portfolio.py:90](D:/fund_ai/src/live_portfolio.py:90)、[live_portfolio.py:249](D:/fund_ai/src/live_portfolio.py:249)。

构造函数只显式指定 `fund_code` 的 dtype。当前 50 行 `execution_date` 全空，pandas 3.0.5 将该列读成 `float64`。在复制真实 ledger/state 后，模拟 10-8 已发生并调用确认，复现：

```text
TypeError: Invalid value '2026-10-08' for dtype 'float64'
```

异常发生在保存之前，磁盘仍为 planned、没有事件，但内存 meta 已变成 active。因此 CLI 路径失败；长驻对象还会留下内存与磁盘不一致。

**建议修改：** 对包括执行日期在内的文本/状态列采用显式可空字符串类型；确认先在副本中完成校验和转换，再提交状态。增加真实往返测试：保存全空执行日期的 planned CSV → 新建对象从 CSV 重载 → 确认 → 再重载 → 重复确认。现有测试直接构造内存 DataFrame，正是遗漏了这一步。

**验收：** 真实台账副本在项目锁定的 pandas 3.0.5 下首次确认成功、重载后仍 active、恰好一条事件；相同重试不新增事件；注入失败后内存与磁盘保持一致。

### P0-2：诊断模式和 `--no-save` 可以污染正式 planned 台账

位置：[production_pipeline.py:364](D:/fund_ai/src/production_pipeline.py:364)、[production_pipeline.py:406](D:/fund_ai/src/production_pipeline.py:406)、[live_portfolio.py:478](D:/fund_ai/src/live_portfolio.py:478)、[live_portfolio.py:484](D:/fund_ai/src/live_portfolio.py:484)。

流水线先调用 `step_portfolio(..., month_end=True)`，随后才决定本次快照是否为 test。因此月末数据上的 `--skip-refresh`/`--skip-clean` 仍会更新正式 planned 选股及 `score_run`。隔离复现中，test 快照成功写出，但 cohort 来源变成没有 COMPLETE 的测试 run，下一次确认反而被“来源不完整”校验拒绝。

独立 CLI 也在 `pf.add_month(scores)` 已经保存之后才处理 `--no-save`；隔离副本中，带 `--no-save` 的命令仍把修改后的基金代码写入 CSV。

另外，`--as-of` 的运行没有独立记录“实时生成/事后重建”的 provenance；不能仅凭 COMPLETE 就把历史重建计为真正前向证据。

**建议修改：** 在触碰正式评分/ledger 前确定运行模式；test、dry-run 应使用独立输出根或纯计算路径。`--no-save` 应控制实际持久化动作。诊断操作前后，对正式 scores/ledger/snapshots 做完整树哈希断言。对 `--as-of` 增加来源时间与重建标注，不把回填混入前向样本。

**验收：** skip/no-save 不改变任何正式文件；test 输出保存在隔离目录，不能更新正式 cohort 的来源。正常正式路径仍引用月末 COMPLETE 快照。

### P1-3：执行修正、事件持久化和快照失败恢复存在不一致窗口

位置：[live_portfolio.py:307](D:/fund_ai/src/live_portfolio.py:307)、[live_portfolio.py:365](D:/fund_ai/src/live_portfolio.py:365)、[live_portfolio.py:427](D:/fund_ai/src/live_portfolio.py:427)、[production_pipeline.py:408](D:/fund_ai/src/production_pipeline.py:408)。

三组已复现的情况：

1. 先确认 10-8，再修正为 10-9。`_latest_exec_event()` 只读 paper/actual，忽略 correction。于是 10-9 重试被拒；10-8 重试返回旧事件并声称幂等，尽管当前状态已是 10-9。
2. correction 的事件追加失败时，日期已经保存成 10-9，事件却仍是 10-8。recover 看见旧事件就返回“无需恢复”，不能修复矛盾。
3. 流水线更新 planned 后，若快照写入失败，正式 planned 仍留着新选股和未完成 run_id。`.bak` 的存在本身不代表已自动回滚。

普通首次确认的 append 异常已有 rollback 测试，是已有优点；上述路径尚未同等覆盖。另从代码可见，save 直接覆盖 CSV 并两次覆盖 JSON，未提供跨文件事务；备份名精度仅到秒，同秒多次 save 可能覆盖备份。

**建议修改：** 从事件流折叠出最终执行事实，correction 包含完整的新执行类型及关联事件；日期、类型重试按最终事实判断。状态、事件及快照使用统一提交/恢复协议，失败后能回到上一完整版本；文件先写临时文件再原子替换，备份采用唯一版本号，恢复核对状态与事件一致性，不能只判断“事件存在”。

**验收：** 修正后新日期重试幂等、旧日期拒绝；注入事件追加或快照复制失败后不留错误来源；重新启动能识别并恢复未完成事务。

## 4. 开始累计前向收益前，还应明确的口径

### P1-4：目标权重台账不是完整的 paper 收益账本

目前代码有目标权重与执行日期，尚未发现前向成交份额、成交净值、现金金额、申赎费用、逐期估值及可执行全池对照的独立账本。`live_portfolio.py` 顶部也明确将收益归属交给调用方，但当前薄工具层没有实现这一完整核算。

此外，有一个实际语义差异值得先写清楚：

- [live_portfolio.py:21](D:/fund_ai/src/live_portfolio.py:21) 声称在持 cohort 不做月度再平衡、自然漂移。
- [backtest_strategy.py:151](D:/fund_ai/src/backtest_strategy.py:151) 对各基金当月收益求简单均值，再对 cohort 求均值。因此回测收益采用每个月的等权算术聚合，并没有用漂移后的份额权重计算。

两只基金初始各 50%，第一个月 A 涨 100%、B 不变，则第二个月权重是 2/3 与 1/3；第二个月 B 涨 100%、A 不变时，自然持有收益是 1/3，而等权当月均值是 1/2。两者不能声称在六批 cohort 到齐后自动完全一致。这里指出的是代码的收益聚合语义，未据此重算全部历史成绩。

**建议先形成前向记账协议：**

1. 保留冻结信号及旧回测；明确其已实现的收益聚合口径与局限。若采用真正份额漂移的 paper 账本，要与历史口径区分并另做对账，不能静默改变后宣称完全一致。
2. 在首次模拟成交时固定规范化初始资本、买入金额/净值/份额、费用、现金计息和到期规则；使用官方日增长率作为收益口径，不能改用累计净值 pct_change。
3. 固定可执行全池的入池集合、同等数据时点及费用口径，并明确前五个月 1/6 递进建仓带来的现金差异怎样比较。9 月快照保存了完整 main 集合，当前仍可据此固定当时基准池。
4. 主策略检验的是相对可执行全池的表现；影子方案才需要另外检验相对原动量的配对增量。原动量不能以“比自己有增量”作为验收条件。
5. 统计评价继续沿用既定冻结纪律与 NW(6)。第一次完整性检查以实际标签结束/可用日为准；126 交易日标签、六个日历月 cohort 和实际执行区间分别记录，不仅凭“2027-03”猜成熟。

这属于必要的执行与测量设计，不是增加选股模型或根据未来收益调策略。纸面确认本身只把状态改成 active；如暂只维护目标台账，应明确标注尚未计算可核验的前向绩效。
